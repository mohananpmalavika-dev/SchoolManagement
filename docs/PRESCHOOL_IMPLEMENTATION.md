# Preschool expansion and deployment

The existing platform now supports regular schools, standalone preschools and combined schools. The preschool workspace uses durable tenant-scoped PostgreSQL records. Existing admissions, fees, payments, calendars, communications and parent accounts remain the shared administration system.

## Activate a school

1. Open **School management → Preschool → School setup** (`/school/preschool`).
2. Select **Playschool / preschool** or **Combined school** for the relevant school. Existing schools default to regular school mode.
3. Select Playgroup, Nursery, LKG or UKG for each preschool class. This sets its education level to `PRE_PRIMARY`.
4. Assign active staff accounts to their preschool classes. An academic timetable is optional for these assignments. Existing timetable assignments also grant access.
5. Enrol children in those classes and link their parent/guardian accounts through the existing student and guardian workflows. Review **Pickup permissions** in daily care.
6. Teachers use `/teacher/preschool`; parents use `/dashboard/preschool`. Standalone preschool navigation hides school-age exams and gradebook workflows and opens the preschool workspace from the default overview. Combined-school navigation retains both sets of tools.

## Included workflows

| Workflow | Behaviour |
|---|---|
| Daily attendance | Server-time check-in updates normal attendance and creates a family update in one transaction. Repeated check-ins conflict. |
| Pickup | Requires a linked guardian with `canPickup`, staff identity verification and an active check-in. Pickup permission changes and checkout serialize on the child record. |
| Daily care | Meals, rest, toileting, mood and notes; explicit parent sharing; version checks prevent overwriting another staff member's edit. |
| Development | Dated observations for language, cognitive, fine/gross motor, social/emotional, self-care and creative skills. Levels are Emerging, Developing and Consistent. Unobserved skills remain unknown. Staff-only observations stay private. |
| Teaching resources | Lesson plans, activities, stories, rhymes, flashcards, colouring, worksheets, games and observation sheets; age range, theme, language, duration and scheduled date. |
| Review and publication | Content saves as a draft. Publishing requires a date, current version and explicit review. Editing a published item returns it to draft. Parents see published scheduled items for their child's class. |
| INKY | Staff-only classroom guidance and suggested activities in English, Malayalam or Hindi. Student records are not loaded into generation requests. |
| Templates / AI | Original editable templates work without an external provider. Configured AI providers use the existing provider service. Template fallback is labelled as a library, rather than external AI output. Teacher review remains required. |
| Printing | Printable teaching text, starter outline/shape worksheets and colouring sheets. Teachers can print or save as PDF using their browser. Starter flashcard words are editable; custom illustrated assets are not generated by this module. |
| Photos | Per-child JPEG/PNG sharing up to 5 MB; teacher-class authorization, signature checks, private object keys and two-minute signed viewing links. The legacy media signing route now checks family/class access too. |
| Reports | Date-range attendance/check-in/out counts, shared care updates, observation counts and admissions. Leadership also sees current outstanding fees. CSV export escapes formula prefixes. Missing attendance records are not counted as absences. |
| Bus | Uses the existing durable transport module with driver-phone GPS, assigned passengers, parent tracking, stale-location handling, labelled approximate ETA and transactional in-app approach/boarding/drop-off alerts. Trips cannot finish with children still onboard. |
| Cameras | Classroom-specific configuration, viewing days/hours in the school timezone, individual parent consent, linked-child authorization, access audits and short-lived allowlisted gateway sessions. |

Parents can view only their linked children. Teachers require an active teaching staff account and an explicit preschool or timetable class assignment. School leadership can configure schools, staff, camera and pickup permissions. New data references use compound tenant foreign keys in addition to application authorization and Prisma tenant filtering.

## Database deployment

Run migrations against a backed-up staging database first, then deploy with the normal release process:

```sh
pnpm db:generate
pnpm db:deploy
pnpm build
```

`202611170001_preschool` adds school programme/class stage settings, preschool records, camera configuration/consent and transport alerts. New school mode defaults to `STANDARD`. Database checks enforce valid care timestamps, ages, durations, versions and viewing windows.

`202611170002_india_schema_alignment` repairs a pre-existing mismatch between the India-oriented application schema and the older migration history. It adds the current Indian payment/compliance tables and fields without dropping historical Kenya-era tables, columns, payment records or enum values. Existing non-Indian school address information is preserved. It changes defaults for future rows, not existing tenant currency or timezone values. Enum additions commit before they are used as defaults.

Historical tables/columns intentionally remain outside the active Prisma model set. A schema diff can therefore report legacy objects as extra. Do not turn such a diff into an automatic destructive migration. Use reviewed forward migrations. An installation previously created through `db push` needs its migration baseline checked before deployment; do not reset a live database.

## Live services to configure

### Driver-phone GPS

Assign a transport officer's linked staff account to each saved route. Add stops with coordinates and assign children to stops. Open the driver workspace on that account's phone, start the trip and enable location sharing. Serve the site over HTTPS and allow browser location access.

The phone browser must remain open; mobile operating systems can suspend background browser location. The UI explains this and shows stale reports. ETA uses straight-line distance and measured/planning speed, not a traffic-aware road-routing service. Approach alerts require an accurate report (at most 100 m uncertainty) within 300 m of the assigned stop. The unique trip/child/alert key prevents repeated approach notifications. Alerts are in-app family updates; SMS, WhatsApp and background push delivery are not enabled by this change.

### Private photos

Configure the existing S3-compatible storage settings (`S3_ENDPOINT`, `S3_REGION`, `S3_BUCKET`, `S3_ACCESS_KEY`, `S3_SECRET_KEY`). Keep the bucket private and verify HTTPS signed-object access from the deployed browser. Unconfigured uploads return an explicit service-unavailable response. Object storage needs a backup and retention policy as part of the existing deployment.

### Classroom CCTV gateway

The camera/NVR provider is not selected yet. Cameras can be configured disabled. This ERP does not transcode RTSP or expose permanent camera credentials. Connect a trusted gateway using all three settings together:

```dotenv
CCTV_GATEWAY_URL=https://camera-gateway.example/api
CCTV_GATEWAY_KEY=<independent gateway credential of at least 32 characters>
CCTV_PLAYBACK_ORIGINS=https://classroom-viewer.example
```

The ERP calls:

```http
POST {CCTV_GATEWAY_URL}/sessions
Authorization: Bearer {CCTV_GATEWAY_KEY}
Content-Type: application/json

{
  "tenantId": "school-tenant-id",
  "cameraRef": "nursery_camera_1",
  "viewerId": "authenticated-user-id",
  "expiresIn": 120
}
```

The gateway must map the tenant and camera reference to the correct stream, authenticate the ERP, and return:

```json
{
  "url": "https://classroom-viewer.example/session/short-lived-token",
  "expiresAt": "2026-11-17T04:32:00.000Z"
}
```

The URL must be an embeddable browser viewer on an exact configured HTTPS origin. The gateway must enforce expiry on the viewer **and every media/segment request**, and must not expose a reusable raw stream URL. Its framing policy must allow the ERP origin. The ERP rejects redirects, unexpected origins, credentials in URLs, expired sessions and sessions lasting over two minutes (with a five-second clock allowance). The viewer closes on local expiry or consent withdrawal. Withdrawal disables new sessions immediately; issued gateway sessions may remain valid until their two-minute expiry. Provider credentials stay on the API server/gateway.

Before enabling a live camera, verify the actual classroom mapping, school-local viewing hours, parent consent, unrelated-parent denial, playback expiry and gateway failure behaviour. Mock gateway tests do not replace this hardware/provider acceptance test.

### Other existing services

Normal production configuration for PostgreSQL, Redis, HTTPS, SMTP, backups, payment gateway credentials and monitoring still applies. Configure and test the actual Razorpay/payment account before accepting online payments. External AI generation requires a working configured provider; templates remain available as a labelled fallback where supported by that provider path.

## Verification

```sh
pnpm --filter @krypton/api type-check
pnpm --filter @krypton/web type-check
pnpm --filter @krypton/api test -- --runInBand
pnpm --filter @krypton/web lint
pnpm build
```

Real database tests require an explicitly supplied isolated database ending in `_test` or `_qa`, after migrations:

```sh
PRESCHOOL_TEST_DATABASE_URL=postgresql://.../krypton_preschool_test pnpm --filter @krypton/api test -- --runInBand preschool.integration.spec
```

The integration suite creates unique fixture tenants and removes its records afterward. It verifies PostgreSQL tenant foreign keys, simultaneous check-ins, conflicting care writes, private parent views, pickup and transport rollback/deduplication.

Migration preservation tests require an **empty** disposable database ending in `_test` and `psql` on PATH (or `PSQL_BIN`):

```sh
PRESCHOOL_MIGRATION_TEST_URL=postgresql://.../krypton_migrations_test pnpm test:db:preschool-migrations
```

Browser workflow checks use a running local web server and mocked APIs:

```sh
UI_BASE_URL=http://127.0.0.1:3102 pnpm test:ui:preschool
```

The browser script verifies check-in, identity-confirmed checkout, care sharing, draft review/publication, printable content, INKY, observations, CSV downloads, teacher/family permissions, safe text rendering and camera-consent behaviour. Screenshots and results are written under ignored `qa/preschool/`. CI runs this browser suite against the production web build, along with the real database and migration-preservation suites. Database integration tests also exercise the NestJS HTTP controller, real JWT authentication, strict input validation, school activation and teacher reassignment.

## Release status

Local verification on 17 November 2026: 33 API test suites / 413 tests passed, including seven real PostgreSQL/HTTP integration tests; six browser workflow checks passed against the optimized production web build; API and web builds and type checks passed. Web lint completed with no errors and 32 existing warnings outside the new preschool components. Complete migration replay and historical-data preservation passed on a separate disposable database. CI definitions were updated; remote CI has not been run from this workspace.

The implementation and local validation can be reviewed independently of deployment. No live school database has been migrated or production service published during this work. A live camera/NVR provider, private storage and real payment/notification configuration must be accepted in the target environment before describing the entire installation as production ready.
